# Data model

## Source of truth

The canonical data is `data/`, validated against `src/schema.ts`. There is no hand-maintained catalog, row count, search index or generated database in source control. `data/relations.json` and `data/navigation.json` contain *curated relationships and order*, which cannot safely be inferred from a category field. The original default order and original TOC order differ, so both represent distinct source facts. Featured membership and order appear only in `navigation.json`.

All content-like strings are interned by exact UTF-8 value in `data/texts/<first-two-hash-characters>.json`. IDs are `t` plus the first 24 hex digits of SHA-256. The builder checks both hash and shard and refuses collisions. There is one empty-string entry because the old English metadata distinguished an empty string from null. Interning itself does not fold or rewrite strings. Occurrences may share a text ID while retaining independent document/row IDs, sources and reviews. A change to one occurrence uses copy-on-write: it cannot silently change every other occurrence.

An explicitly requested punctuation-spacing correction changes the current canonical content, not merely its display. Each affected occurrence has a recorded previous and replacement text ID in `editorial-history.json`, and both exact values remain in the pool. Row and paragraph IDs, claims, existing editorial entries, provenance and review status are not rewritten. This mechanical correction does not establish textual accuracy or rights. Because spaces were removed or inserted within some rows (including the audited Quran end-marker spacing), older links containing character offsets can land slightly differently within the same row; newly generated search links use the corrected offsets.

A literal reference is not a duplicated text. Repeated recitations and identical phrases can still appear multiple times as *occurrences* in their original order; this is necessary to represent the content faithfully. Do not remove an occurrence just because its text ID appears elsewhere.

The targeted audit retired 37 English paragraph locations after preserving their exact text in another document. Their old `(document, paragraph)` keys are reserved, not recycled. `data/editorial-history.json` maps each to its preserved destination and historical text ID; `resolveEnglishParagraph` follows that mapping in TypeScript. The web-data build emits `paragraph-redirects.json` and `paragraph_redirects` in each affected English document; SQLite exposes the same mapping as the `paragraph_redirect` view. Clients must explicitly follow these redirects for old bookmarks; there is no website/router yet. A redirect preserves a paragraph reference, **not** an incorrect item–document link or an approval of a proposed link.

## Items, rows, English documents and links

- `items/<slug>.json`: a stable slug from its filename; optional legacy ID; title references, category, tag references, ordered rows, optional source IDs and reviews. Whole-surah items can carry a structured Quran chapter number. A row has a stable ID and optional Arabic and Persian text references. Both empty is invalid. An empty Arabic field does not necessarily mean a note. `kind` can be supplied after classification.
- `row-splits/<item>.json`: when the six-agent canonical tool has processed an item, this records the original row structures and exact source-language/code-point slices leading to current rows and language fields. V1 targets offset zero; V2 records `target_start` and prior-output aliases when explicitly reviewed adjacent rows are concatenated. Old pooled values remain referenced; retired row IDs are not reused. The reader follows both original and alias mappings for old row/offset links. Whole-item bookmarks retain their item IDs. The tool refuses to migrate existing human-reviewed alignments or compose arbitrary earlier-round split mappings automatically.
- `english/<id>.json`: stable document ID, original metadata/claims, optional editorial display-title override, coverage status and ordered paragraph occurrences. The override, when present, is the display title; `source_metadata` records the historical title and is not a second current value. If a metadata title is ever changed by the punctuation-spacing workflow, its exact previous value and occurrence are retained in punctuation history. A paragraph has its own stable ID even when its text is shared. Document-level sources can be overridden at paragraph level.
- `relations.json`: the item–document relationship exists in one place. `legacy-primary`, `legacy-primary-only`, `legacy-coverage`, `proposed-quran` and `proposed` describe how a link arose; a separate reviewer/date marks a link as reviewed without erasing its history. A document may link to more than one item and an item may link to more than one document.
- `editorial-history.json`: auditable corrections, row insertions/classifications, paragraph detachments, source-document splits, retracted and proposed links, supporting evidence, occurrence-level punctuation-spacing corrections, explicitly mapped line-break marker moves, and reversible navigation page corrections. Marker moves record source/destination row IDs and both old/new text references and are checked against the associated row corrections. Text corrections use pooled references; page corrections retain raw numeric values, optional-field presence and source-footer observations. Navigation paths in history are positions at the time of correction, not permanent IDs. Current item/row/document/navigation values remain authoritative. The metadata evidence also records the chapter-number cross-check.
- `claims.json`: preserved statements from the old provenance ledger; a claim is not proof of accuracy or permission. Old document-level claims may cover mixed-source paragraphs. The original per-paragraph claims and source notes are retained where present.
- `sources.json`: structured source, edition, attribution, license, evidence and allowed-use records. Six comparison-source records exist, all `unverified`; a match to a reference is not proof of the corpus's original source or a permission. Source IDs can be assigned separately to Arabic and Persian at item or row level, or to English at document or paragraph level.

`navigation.json` associates known positive source pages with `source_page_series` (`front-matter` or `main`), because the compared edition resets numbering. Unknowns are null or, for an end, an absent key; a known end cannot precede its start. Group ends may be inferred subtree extents rather than independently reviewed work boundaries. The source comparison, exceptions, exact prior values and reproduction instructions are in [source-page metadata](source-pages.md).

Do not assume `coverage: "unknown"` means a body translation exists. Do not align or display an English introduction as if it translated a prayer. The old `manual-v1` flag is retained in `legacy_alignment`, but means only that the previous dataset asserted manual AR/FA alignment.

## Fine and coarse alignment

`data/alignments/<item>.json` holds reviewed groups with arrays of AR, FA and EN spans. Each Arabic/Persian span names a row ID; each English span names a document and paragraph ID. Spans use zero-based, half-open **Unicode code-point** offsets, not byte offsets or JavaScript UTF-16 code units. A group can contain multiple spans per language and can represent 1:1, 1:N, N:1, N:M, or an AR–EN link without an asserted FA sub-span.

A SHA-256 fingerprint records the exact reviewed span. Validation rejects a stale span if the source changes. Row/paragraph identities are stable; the six-agent split tool retires changed row IDs and records exact redirects, while keeping item-level bookmarks intact. It refuses items with existing human text reviews or alignments instead of silently migrating them. Never reuse an old ID for unrelated content. Reviews are human assertions and must identify a reviewer and date; automatic matching is never labelled reviewed.

## Artifacts and storage

The TypeScript build generates resolved, lazy-loadable JSON and a normalized search artifact. It does not further rewrite canonical content; the same `normalizeSearch` function handles indexing and queries. The version 4 search manifest contains TOC records and paths to generated Arabic/Persian row-field shards; search normalization is tagged `nfkd-search-v2`. Immediately adjacent source rows in the same item and language may be linked for compact sequence ranking, without joining a word across a row boundary or combining arbitrary scattered words across an item. TOC and text compete in one ranked list: displayed distinct matched-term count comes first, then starred status, followed by relevance/sequence and deterministic tie-breakers including TOC status. Join controls do not split a search word. A constrained ordinary-space fallback supports some joined/spaced spellings without joining arbitrary word fragments, but it is still a heuristic and can conflate different phrases. See [search behavior and tests](search-behavior.md). English search is not implemented yet.

`npm run build:sqlite` generates a normalized SQLite database with foreign keys and editorial-history tables, including `punctuation_normalization`, `punctuation_correction`, `line_break_marker_move`, `navigation_page_batch` and `navigation_page_correction`. SQLite schema version 4 preserves page series, retired `row_identity` records and reversible split/merge mappings. `row_split_segment.target_start_cp` gives the destination code-point offset; `row_split_original.origin_kind` distinguishes frozen originals from prior-output aliases. V1 offsets export as zero. Regenerate old derived databases rather than treating them as canonical. Its `text_value` table stores each exact text once; row and paragraph occurrences reference it. It includes all canonical rows, including 28 currently classified `kind = 'audio-reciter'` rows. By contrast the development web-data builder omits those rows from item content and search and records `excluded_audio_rows` on each item. It has no FTS promise: the website search index is a separate generated JSON artifact. Use it only if a future client chooses an appropriate SQLite adapter.

Example SQL after building the database:

```sql
SELECT r.row_id, ar.value AS arabic, fa.value AS persian
FROM item_row AS r
LEFT JOIN text_value AS ar ON ar.id = r.ar_text_id
LEFT JOIN text_value AS fa ON fa.id = r.fa_text_id
WHERE r.item_id = 'dua-kumayl'
ORDER BY r.position;
```
