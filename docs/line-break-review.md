# In-row line breaks: corrections and pending review

The 2026-11-06 AI-assisted, user-requested pass assessed 326 physical LF occurrences in the then-current 314 Arabic/Persian row fields. It joined **238 breaks in 237 fields** (31 items) where the local context was judged to be an unintended interruption or a punctuation-only continuation. This is a formatting assessment, **not an expert content, translation, alignment or rights review**. No rows were merged; item, row and paragraph IDs and existing alignment claims and reviews were retained. All 314 affected pre-edit fields had the same break type/count in the preserved legacy snapshot `b992be9`; that comparison does not establish intent. Original exact text IDs and values remain in the pool and in the occurrence-level `row_corrections` of `data/editorial-history.json`.

Ten breaks in `ziyarat-ashura` were joined. In `r00003/fa`, a comma follows the preceding text without a space. In `r00032/ar`, the break was between two adjacent semicolons; one duplicate semicolon was removed explicitly, preserving the original value. A separate published presentation was used only as a punctuation cross-check, with its URL and limitations recorded in editorial evidence. The edit is unreviewed, and no recited words were changed.

**88 existing breaks remain pending source/human review**, not automatically approved: 61 may separate paragraphs or distinct supplications, 16 involve introduction list/quotation structure, three involve misplaced Jawshan section numbers, one separates a complete sentence from an invocation, one separates distinct excerpts in `dua-samat/r00117/fa`, one separates repeated invocations in `monajat-mnajat-aymh-alyhm/r00020/ar`, one precedes a dash at an instruction boundary in `ziyarat-jamea-kabira/r00313/ar`, three involve ambiguous repeated periods (one separated by a closing quote), and one borders a standalone ellipsis. Several list markers appear at the end of one row before material in another; the pass did not move them across rows. Keeping a break does not prove it is intentional. Repetitions and ambiguous punctuation were not silently removed.

## Future checks

```sh
npm run check:line-breaks           # also part of npm run check / CI
npm run check:line-breaks -- --list # location, exact text ID, code-point offset, context and reason
npm --silent run check:line-breaks -- --json # machine-readable report
```

The guard scans active pooled item titles, tags, row fields (including excluded audio rows), English titles, source metadata and paragraphs, navigation titles, source display fields and source claims. It does not scan old values retained *only* in editorial history. It detects LF, CRLF, CR, NEL, Unicode line/paragraph separators, vertical tab and form feed. Soft visual wrapping is not a physical separator and is not flagged.

`data/line-break-exceptions.json` pins each retained break to its stable location, current content-addressed text ID, separator kind and zero-based **Unicode code-point** offset. All entries from this pass are `pending` and require a meaningful reason. The check fails on newly introduced, removed, moved, differently encoded, duplicated or text-changed exceptions. Thus editing a field with an excepted break requires rechecking that occurrence even if the break was not the intended edit. It also rejects pooled text edited in place without a new content ID.

To resolve a pending entry, inspect its surrounding row and neighboring source rows against appropriate evidence. Use the existing copy-on-write editing workflow; preserve the original ID/value, record the occurrence and evidence in editorial history, and respect reviewed alignment spans. Remove the exception if the break was removed, or explicitly update its exact current ID/offset/kind and reason if it must remain. If an intentional new break is required, add an explicit `pending` exception after inspecting it. A retained break can be marked `reviewed` **only after genuine human review**, by adding a `review` object with `reviewer`, real ISO `date`, and an `evidence` description identifying what was checked. The guard validates these fields but cannot verify their truth or certify a source/rights decision. Never bulk-join paragraphs, move list markers across rows, remove meaningful repetitions or invent translations just to make the check pass. Re-run `npm run check`, and obtain the necessary human/rights reviews before publication.
